为当前仓库设置或优化面向代理的开发。基于OpenAI的工程实践和HumanLayer的CLAUDE.md指南。

额外的用户上下文和约束：

$ARGUMENTS

在做出任何更改之前：

1. 首先检查仓库状态。
2. 将仓库与以下清单进行对比。
3. 优先选择最小化、高杠杆、版本化的更改。
4. 保留有用的项目特定指导，而不是盲目替换。

## 使用场景

- 为新仓库设置代理驱动的开发
- 优化现有仓库的AGENTS.md / CLAUDE.md
- 重构文档以提高代理的可读性

## 核心原则

### 1. AGENTS.md = 目录，而非百科全书

- **最多约100行。** 简短、稳定的入口点。
- 仅包含普遍适用的指令（适用于每个任务）。
- 指向更深层次的信息源，而非包含它们。
- 领域特定规则放在子文件中（`docs/`、技能或子目录中的AGENTS.md）。

### 2. 渐进式信息呈现

- 代理从一个小的地图开始，并被告知下一步该看哪里。
- 在子目录中使用嵌套的AGENTS.md文件提供范围化的上下文。
- 技能用于领域特定的工作流程（按需加载，而非始终加载）。
- 不要一次性加载所有信息——让代理根据需要发现上下文。

### 3. 仓库 = 记录系统

- 如果不在仓库中，代理就无法知晓。
- 将决策、架构、计划、约定作为版本化的工件推入仓库。
- 不要在Slack、Google Docs或人们的头脑中保留隐性知识。
- 文档即代码——它们需要被审查、更新和维护。

### 4. 代理可读性优先

- 优化代理的理解能力，而不仅仅是人类的可读性。
- 偏好“无聊”的技术——可组合、稳定的API，在训练数据中有良好表现。
- 使应用可检查：日志、指标、测试输出应能被代理解析。
- 结构化格式（JSON、带有清晰标题的Markdown）优于大段文字。

### 5. 强制执行，而非指导

- 通过CI/代码检查工具强制执行的不变量优于AGENTS.md中的指令。
- 类型检查、测试、格式化规则能机械地捕捉错误。
- 代理可以自行运行验证（`make check`、`npm test`等）。
- 代理无法验证的指令最终会被忽略。

### 6. 指令越少，合规性越好

- 大型语言模型可靠地遵循约150-200条指令（前沿思维模型）。
- 代理框架已在系统提示中消耗约50条指令。
- AGENTS.md中的每条指令都在争夺注意力预算。
- 当所有内容都“重要”时，就没有真正重要的了。

## AGENTS.md模板

```markdown
# AGENTS.md

## 项目

<1-2句话：这个项目是什么以及做什么>

## 技术栈

<关键技术的项目符号列表：语言、框架、数据库、基础设施>

## 结构

<关键目录及其内容的简要地图>

## 开发

<如何构建、运行、测试——基本命令>

## 文档

详细文档位于`docs/`：

- `docs/ARCHITECTURE.md` — 系统设计、包分层、领域地图

- `docs/CONVENTIONS.md` — 代码风格、模式、命名

- `docs/PLANS.md` — 活跃的执行计划和进度

- `docs/DECISIONS.md` — 架构决策记录（ADR）

## 验证

<如何验证更改：测试命令、类型检查、代码检查工具>

## 规则

<仅包含普遍适用、始终适用的规则——保持在10条以内>
```

## docs/结构

```

docs/
├── ARCHITECTURE.md # 系统设计、领域地图、包分层
├── CONVENTIONS.md # 代码风格、模式、命名约定
├── DECISIONS.md # 架构决策记录（ADR）
├── PLANS.md # 活跃计划、已完成计划、技术债务
└── <domain>/ # 按需的领域特定深度文档

```

## AGENTS.md ↔ CLAUDE.md 符号链接

始终确保两个文件都存在，以便仓库能与任何代理框架（Claude Code、OpenCode、Codex等）兼容。

- `AGENTS.md` 是真相来源（规范文件）。
