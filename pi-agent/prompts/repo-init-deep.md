为以代理优先的开发设置或优化当前仓库，假设它可能是一个大型仓库或单体仓库。仅在真正增加价值的地方使用分层 `AGENTS.md` 文件。基于 OpenAI 的 harness 工程和 HumanLayer 的 CLAUDE.md 指南的原则。

额外的用户上下文和约束：

$ARGUMENTS

在更改任何内容之前：

1. 首先检查仓库结构。
2. 在提议嵌套 `AGENTS.md` 文件之前，识别真正的子系统边界。
3. 优先选择最小、高杠杆、版本化的更改。
4. 保留有用的项目特定指导，而不是盲目替换。
5. **不要**为每个目录生成 `AGENTS.md` 文件。

## 何时使用

- 包含多个领域、应用、服务或包的大型仓库
- 每个子树具有不同构建/测试工作流的单体仓库
- 根 `AGENTS.md` 过于宽泛而难以保持简短和有用的仓库
- 需要为代理上下文进行渐进式披露的仓库

## 目标

设计一个代理可读的文档布局，其中：

- 根 `AGENTS.md` 保持简短且覆盖整个仓库，
- 嵌套 `AGENTS.md` 文件仅存在于有意义的边界处，
- 每个嵌套文件包含该子树的本地规则、命令和导航帮助，
- 各层级之间的重复最小化。

## 核心原则

### 1. 根 AGENTS.md 是地图

- 根 `AGENTS.md` 应保持为简洁的项目级入口点。
- 它应描述仓库、主要子系统、共享命令、验证以及更深层上下文的位置。
- 它应引导代理指向具有自己 `AGENTS.md` 的重要子树。

### 2. 嵌套 AGENTS.md 文件是范围限定的

仅当子树至少满足以下条件之一时，才创建嵌套 `AGENTS.md` 文件：

- 具有不同的目的或领域边界，
- 具有不同的命令或验证工作流，
- 具有不同的约定或架构约束，
- 具有独立的部署/运行时关注点，
- 具有足够的复杂性，使得本地指导能减少混淆。

如果子树没有独特的指导，**不要**在那里创建嵌套 `AGENTS.md`。

### 3. 渐进式披露优于重复

- 父文件提供广泛上下文。
- 子文件仅添加本地上下文。
- 不要将相同的规则复制到每个嵌套文件中。
- 子文件应扩展或缩小父上下文，而不是重述。

### 4. 仓库 = 记录系统

- 如果某个决策对代理重要，将其放入仓库。
- 架构、约定、计划和决策应存在于版本化的文档中。
- 避免依赖仅外部知识。

### 5. 强制执行，而非指导

- 尽可能将不变性放入 CI、测试、linter、类型检查和脚本中。
- 记录代理可以实际运行的验证命令。
- 避免无法机械检查的指令。

### 6. 更少的指令 = 更好的合规性

- 保持每个 `AGENTS.md` 紧凑。
- 根文件通常应保持在约 100 行以下。
- 嵌套文件应更窄：仅包含对该子树重要的本地规则。

## 建议的层级结构

仅按需使用，而非默认：

```text

project/
├── AGENTS.md # 项目级上下文和仓库地图
├── CLAUDE.md -> AGENTS.md
├── docs/
│ ├── ARCHITECTURE.md
│ ├── CONVENTIONS.md
│ ├── DECISIONS.md
│ └── PLANS.md
├── apps/
│ ├── AGENTS.md # 应用层指导，如有意义
│ ├── web/
│ │ └── AGENTS.md # 仅当 web 有独特工作流/约定时
│ └── api/
│ └── AGENTS.md # 仅当 api 有独特工作流/约定时
└── packages/
├── AGENTS.md # 共享包约定，如有意义
└── design-system/
└── AGENTS.md # 仅当此子树需要额外本地指导时

```

## 添加嵌套 AGENTS.md 的启发式方法

好的候选：

- `apps/`、`services/`、`packages/`、`libs/`
- 前端与后端边界
- 基础设施/部署/运维目录
- 设计系统或组件库
- 具有特殊规则的生成代码边界
- 具有自己测试/构建/开发命令的领域
  差的候选：

- 没有本地规则的浅层文件夹
- 仅反映代码组织而非工作流差异的目录
- 树中的每个叶子文件夹
- 嵌套文件只会重复父文件
